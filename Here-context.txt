1. WHAT "HERE" IS
--------------------------------------------------------------------------------
HERE is a prototype/revamp of a live product at now.hereandmore.com — a social
layer that sits on top of CRM-based platforms and services. It is being built
"against the original rather than beside it": on 15 September 2026 the
prototype was deliberately matched to the live app's latest update — same
warm palette and rust brand, same card geometry, same shell, navigation,
screen names and page descriptions. Desktop layout on desktop, the shipped
mobile shell on phone, light and dark throughout.

Local repo path: /Users/amanporwal/Desktop/Here/HERE
Git remote: https://everything.hereandmore.com/garden/HERE.git
  (moved from the older `beato/HERE` URL by 15 Sep 2026 — that old URL now
  redirects, which silently breaks pushes if someone still has it as a remote.
  Check `git remote -v` before pushing.)
Intended application integration target: https://now.hereandmore.com
IMPORTANT: a successful `git push` to the repo is NOT evidence the application
was deployed. The repo and the live app are two different destinations.

This is a static-frontend prototype: no build step, hash-routed single-page
app (`index.html`), served by anything that hands back static files, or via
a small local Python dev server (`server.py`, `--test` mode) for previewing
Teams/Rooms without a real backend.


2. THE PRODUCT / TERMINOLOGY MODEL (from a separate architecture memo)
--------------------------------------------------------------------------------
A companion product-direction document (not code, a decision memo dated
12 September 2026) lays out how HERE relates to sibling services. This is
useful background for anyone reasoning about identity, spending, or scope
boundaries — it predates and is independent of the monetization plan below,
but the monetization plan's Tier 7 (Dialog pass-through) and the "every
action is a tool" framing both lean on it.

Layers / services and their responsibility:
  - JEM        — shared identity, sign-in, and authority/access relationships.
                 A JEM identity does NOT require participating in every
                 service (you can hold a JEM login and only ever use Dialog,
                 or only ever use HERE, never both).
  - HERE       — social relationships, SCircles, CRM context, and a shared
                 map of understanding across Capture, Broadcast and
                 Rooms/messages. Design/build collaboration happens here.
  - IDS studio — the design and build harness: briefs, versions, chosen
                 tools/LLMs, HERE mappings, reviews, deployment approvals,
                 results.
  - Dialog     — a SEPARATE, specialised service for serious legal/financial
                 conversations, on-camera contracting, shared matter
                 intelligence, each party's private analysis. Has its own,
                 separately authorised expenditure. A HERE conversation can
                 hand off into Dialog deliberately (with a purpose/context/
                 audience/budget preview), but a paid HERE action does NOT by
                 itself make something a Dialog matter, and Dialog does not
                 require prior HERE membership.
  - RTracer, The Garden, other services — their own communities/workflows,
                 connected to HERE only through permitted, source-specific
                 integrations.
  - Everything — the continuing record of source material, versions,
                 relationships and outcomes.

Vocabulary used across product docs and the monetization plan:
  - Scircles  — "worlds" / collections of rooms with shared perspectives;
                visually represented as 4D orbs, with data shown as 2D
                slices/layers ("frequencies"/sounds). A person's ego,
                personality, wishes and destiny shape the Scircles they're in.
  - Spaces    — within/across rooms; "angular temporal perspectives."
  - Rooms     — chat/collaboration surfaces inside a Scircle (formerly
                "Messages" in this codebase — see naming table below).
  - Wellim / Prive — a concierge-agent concept ("well I am") that manages a
                person's needs across their network of Scircles. Not yet
                built in this repo; product-vision language only.
  - US        — the publicly-facing social interface for managing Scircles.
  - HERE (as a "game")  — the on-demand MMO/game framing: HERE can disappear
                from view/thought and be "reinvoked into form" when a moment
                becomes demanding/exciting enough; as "velocity rises," UI
                "cockpits" take shape. JEM is the central authority/author of
                this framing ("the Golden Film of Ascension").
  - NOW       — the command-center / dashboard for people actively "playing"
                (PRIME users): billing, credit assignment, vendor connections,
                and whether "GO" scripting is authorised. NOW is where the
                monetization plan's GO-card/authorisation gate lives.
  - GO        — the authorisation/spend decision point. "Whether the GO
                scripting is possible" = whether an action is allowed to
                spend money. This term is reused literally in the credit
                system's flow (QUOTE → GO CARD → HOLD → RUN → SETTLE →
                LEDGER — see the monetization file).
  - IGNI      — mentioned as the mechanism that "jumps into the mind of
                Wellim/Prive" — a personalization/orchestration concept.
                Not yet built; no code references found in this repo.

5. GUARDIANS: THE MODEL LIST THE MONETIZATION PLAN IS BUILT ON
--------------------------------------------------------------------------------
From `assets/agents-data.js` (Anthropic API IDs + list prices per million
input/output tokens, as published June 2026 — re-check before any release,
production should pull from the Models API + workspace policy):

  Model            | API id            | Context | $/M in | $/M out | Notes
  -----------------|--------------------|---------|--------|---------|---------------
  Claude Haiku 4.5 | claude-haiku-4-5   | 200K    | $1     | $5      |
  Claude Sonnet 5  | claude-sonnet-5    | 1M      | $2     | $10     |
  Claude Opus 5    | claude-opus-5      | 1M      | $5     | $25     | current default
  Claude Fable 5.1 | claude-fable-5-1   | 1M      | $10    | $50     | 30-day data
                                                                        retention
                                                                        requirement

The Guardians recommendation engine sums each model's fit (0–3) over chosen
needs; ties go to the model with the higher weakest-fit, then Opus 5 >
Sonnet 5 > Fable 5.1 > Haiku 4.5. A typical run is estimated at 20K input +
2K output tokens (this exact run size is what the monetization plan's
per-action credit pricing is computed from — see the other file).

Each Guardian instance (however "instance" ends up being defined — see the
OPEN QUESTIONS in the monetization file, this is blocking) costs the business
$500/month, fixed, regardless of usage. This one fact is the reason the
monetization plan rejects a pure pay-as-you-go credit model in favor of a
subscription-plus-metered-credits ("two-part tariff") design.

Guardians boundary facts (from AGENT-BUILDER.md, "Specialized-agent prototype
boundary"):
  - No model, MCP server, OAuth flow, webhook or scheduler is actually
    contacted by the specialized-guardian builder yet — it's a prototype
    that simulates deployment after save.
  - No credentials are requested or stored; custom MCP URLs must be https://
    and may not contain a username/password.
  - Guardians belong to one browser profile (IndexedDB/localStorage) —
    clearing site data removes them; other people on the same profile can
    see them. There is no server-side guardian store yet.
  - The "HERE workspace MCP servers" referenced in the vision don't exist
    yet either. Broadcast recordings currently live in each browser's
    IndexedDB (see BROADCAST-HANDOFF.md) — a guardian can't read them until
    they're stored server-side.
